# v3.2.4 · 蓝牙协商与诊断优化

- 减少预设测试中的反复切换。较差候选直接进入下一项，最终复核前按需恢复最佳请求；若最后一项本来就是最佳请求，不重复下发。请求失败或中途取消时按“当前请求状态未知”处理，保留必要的恢复动作。多手柄受到影响时仍立即恢复原请求。
- 补齐高速首窗复核降到兼容速率的分支。最终仍满足 60Hz、新鲜度、解析和间隙要求且优于原连接时，可以保留兼容方案；133Hz 级验收标准不放宽。
- 区分“请求是否成功”和“测量是否有效”。纯测量窗口不需要假装又发出一次成功请求，也不会改写测量中的原始标志。
- 补齐蓝牙恢复的待重启判断。识别设备状态中的 DN_NEED_RESTART／Code 14，以及 exit=50 对应的明确中英文“等待系统重启以完成先前操作”提示。普通不支持错误和笼统的 restart 字样不算待重启证据。记录被截断时仍保留已识别的证据。
- CLI 进度改为同步接收，并在同一锁内生成日志时间、递增序号和 QPC 时间。序号代表日志接收顺序，不代表无线事件的绝对先后；系统时间校正也不会改变日志序号。
- 每个参数测量窗口新增 `DeviceTiming`：设备运动时间戳间隔 P50／P95、主机与设备间隔差最大值、counter 原始步进分布，以及重复、时钟跳变、回调顺序调整和容量截断计数。结果写入 `WIN11_PARAMETER_TRIAL`、诊断 JSON 和“系统与蓝牙信息”。

设备时间统计采用固定容量，通知回调只记录原始字段；排序和百分位计算在窗口结束、解除接收锁后完成。按现有协议观察以 1000 个 motion timestamp 原始单位/ms 换算，并保留原始推进量；此比例不是所有固件的保证。

这些差值仅比较相邻已收到的报告。若中间报告没有交付，设备时间戳同样可能跳变，因此匹配的 7.5／22.5ms 双峰不能单独证明固件漏发；较大差值也不能单独区分空口重传、控制器调度与 Windows 交付延迟。诊断不会自动给出“100% 固件故障”或“100% 无线丢包”的结论。

验证：931432 项离线断言通过，包含历史四预设数据回放、最后一项为最佳、失败请求释放旧参数、高速转兼容、取消和多手柄保护、待重启中英文与反例、并发日志顺序、设备时钟回绕／重复／复位／乱序与容量上限。

本版本未改驱动、注册表、配对或当前蓝牙连接。本轮未做实机 133Hz 或长时间待机验收，不能沿用 v3.2.3 的 60 秒实测作为本版本的实测结论。

实现依据：[PnPUtil 返回值](https://learn.microsoft.com/en-us/windows-hardware/drivers/devtest/pnputil-return-values)、[Code 14](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/cm-prob-need-restart)、[DN_NEED_RESTART 状态说明](https://learn.microsoft.com/en-us/windows-hardware/drivers/wdtf/attribute-tokens-in-sdel)、[错误码 50](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--0-499-)。
